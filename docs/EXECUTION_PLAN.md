# Cairn Execution Plan

**Version:** 1.0, 2026-11-24
**Companion documents:** [SPEC_V2.md](SPEC_V2.md), [ROADMAP.md](ROADMAP.md),
[SAFETY_RULES.md](SAFETY_RULES.md)

This is the build plan. It is ordered by risk retirement, not by feature appeal. The
first job is to make wrong behavior impossible to ship quietly. The second is to
prove the core on one device family. Breadth comes last.

---

## 1. Operating assumptions

- **Team:** one lead engineer (full-time) plus AI pair and part-time safety/hardware
  review. Timelines below are engineering weeks and assume this. Add 30-50% for a
  solo schedule with no hardware help.
- **Hardware:** at least two sacrificial devices per target family. Never a daily
  driver. A test device can be destroyed; the plan budgets for it.
- **Platforms:** Windows 10/11 first (repair-shop reality), Ubuntu second.
- **Release shape:** Apache-2.0 core, signed catalog as a separate commercial asset,
  opt-in telemetry.
- **No real-device writes** before the M6 gate and a documented recovery drill.
- **No auth bypass, ever.** This constrains MediaTek/Unisoc scope and is not
  negotiable.
- **One source of truth:** the spec, safety rules, decisions, unknowns, and hardware
  findings live in this repo. Chat context is not documentation.

### Cadence

- One-week thin slices; demo every Friday.
- A milestone is not done until its acceptance test runs in CI or on hardware and the
  result is recorded.
- Every safety rule change requires a mutation test and a source citation.
- Every real-device run produces a `HARDWARE_FINDINGS.md` entry and, where possible,
  a scrubbed transcript fixture.

## 4. First fifteen tasks

These are ticket-ready. Each has an acceptance test; "code exists" is not done.

### T01 - Repo and CI foundation (done)

**Deliverable:** repo, Apache-2.0 license, `pyproject.toml`, uv, ruff, mypy strict,
pytest, Hypothesis, CI on Ubuntu and Windows.
**Accept:** `uv run ruff check .`, `uv run ruff format --check .`,
`uv run mypy src`, `uv run pytest -q` all pass; CI green.
**Status:** scaffold landed in the initial commit. CI verification is part of T01's
close-out.

### T02 - Sparse oracle harness

**Deliverable:** fixtures generated by `img2simg`; round-trip and malformed-input
tests against `simg2img`; skip-with-reason only when the oracle is absent locally
(CI installs it).
**Accept:** every parser constant and header field is covered; a mutated constant
fails the suite; malformed images are rejected identically to libsparse for the
covered cases.
**Depends on:** T01.
**Status:** harness landed and green in CI (run `45500165412`): the dedicated Ubuntu
job installs `android-sdk-libsparse-utils` and the `img2simg`/`simg2img` round trip
passes. Locally the oracle skips with a reason when libsparse is absent. Malformed
cases are covered by unit tests but not yet differentially compared with libsparse.

### T03 - Evidence graph completion

**Deliverable:** evidence IDs, graph storage, freshness-at-use, post-reboot
invalidation, source strength ordering, serialization.
**Accept:** property tests for freshness and strength; a probe before reboot cannot
satisfy a post-reboot precondition; inferred evidence is never usable.
**Depends on:** T01.
**Status:** landed (2026-11-25). Evidence IDs are deterministic and verified on load;
the graph stamps facts with a boot epoch, invalidates earlier epochs on reboot, refuses
inferred and stale evidence, and survives JSON persistence. Units and source-strength
property tests are green.

### T04 - Subprocess wrapper and tool manifest

**Deliverable:** streaming subprocess runner with timeouts, cancellation, bounded
buffers, no shell, environment scrubbing; tool manifest with version, hash, minimum
version, and license.
**Accept:** simulated hang/timeout/cancel tests; a tool below minimum version is
refused; the exact version is journaled; GPL tools are only invoked as separate
processes.
**Depends on:** T01.
**Status:** runner, manifest, and tests landed (2026-11-25). Environment scrubbing,
bounded buffers, timeout, cancellation, SHA-256 and minimum-version checks are
covered. Journaling the verified version waits for the M5 journal.

### T05 - Fastboot simulator with transcripts

**Deliverable:** transcript schema, recorder/replayer, fault injection (timeout,
truncated response, `FAIL`, disconnect), `getvar all` replay.
**Accept:** simulator answers a recorded Pixel-class `getvar all`; injected faults
produce classified errors, not crashes; fixture is scrubbed.
**Depends on:** T01, T04.
**Status:** schema, recorder, replayer, faults (timeout, truncated, disconnect, fail,
garbage), and a scrubbed synthetic fixture landed (2026-11-25). Simulated evidence is
forced to `INFERRED` so it can never satisfy a safety rule.

### T06 - Fastboot adapter, read-only

**Deliverable:** detect, `getvar`, slot/capability/battery probes, lock state, device
identity. No write path yet.
**Accept:** adapter passes against simulator and one real device; every fact carries
provenance and freshness; unknown values stay `UNKNOWN`.
**Depends on:** T05.
**Status:** partial (2026-11-25). Read-only `getvar all`/`getvar`, provenance,
freshness, and fail-closed classification pass against the simulator; one real-device
run is still required. Slot signals are recorded as `UNKNOWN` values until a hardware
finding confirms their semantics.

### T07 - Host Doctor MVP and link soak

**Deliverable:** Windows driver presence checks, USB topology, power/sleep checks,
WSL/VM warning, antivirus heuristic, soak test using `getvar` and staged `download`.
**Accept:** a bad cable/port/hub scenario is detected and blocks; a healthy setup
passes; results are recorded with thresholds and tool versions.
**Depends on:** T04, T06.
**Status:** MVP landed (2026-11-25). Read-only checks cover WSL/VM, USB controllers,
a Windows driver-package heuristic, USB selective suspend, antivirus heuristics,
tool versions, and a bounded `getvar` soak with explicit failure/latency thresholds.
A failed soak is FALSE and blocks. Staged-download soak and USB topology depth remain
pending.

### T08 - Package parsers and unified manifest

**Deliverable:** factory zip, `fastboot-info.txt`, sparse images, OTA metadata
read-only, unified `PackageManifest`.
**Accept:** golden fixtures for at least three vendor packages; unknown files are
reported, not ignored; malformed archives fail closed.
**Depends on:** T02, T04.
**Status:** partial (2026-11-25). The AOSP v1 `fastboot-info.txt` grammar, full
sparse-image validation, factory/OTA zip inspection, OTA metadata, and the unified
`PackageManifest` are implemented, with a read-only `cairn inspect`. Synthetic
fixtures cover the parsers; golden fixtures for three real vendor packages are still
required, and nested factory image zips are reported but not opened.

### T09 - Provenance and AVB chain verification

**Deliverable:** vendor hash index, `avbtool` chain-following verification, VBMeta
digest, lock-state-aware key check, `pixel_factory_image_verify.py` oracle.
**Accept:** matches `avbtool` and the Pixel verifier on a corpus; chained VBMeta and
per-location rollback indexes are handled; unknown package is Assisted, not Verified.
**Depends on:** T08.
**Status:** partial (2026-11-25). The offline vendor hash index and `cairn provenance`
are implemented with strict schema validation, archive/entry hash comparison, and
tri-state results; a local index match is explicitly not a signature check. A strict
read-only VBMeta parser (`provenance/avb.py`) and `cairn avb info|digest|verify`
now parse standalone, padded, and footer-embedded VBMeta headers and hash,
hashtree, chain, property, and kernel cmdline descriptors, compute the AOSP digest
from supplied chained images, and verify the VBMeta RSA signature against the
embedded key with an optional expected raw AVB public key. Chain-of-trust
verification (`verify_vbmeta_chain`, `cairn avb verify --chain NAME=PATH`) checks
that each chain descriptor's key equals the chained image's embedded key, that the
chained signature validates, that the descriptor rollback location is non-zero
while the chained header location is zero, and that nested chains hold, with
tri-state fail-closed results where FALSE outranks UNKNOWN outranks TRUE. AOSP
avbtool-generated unsigned, signed, footer, and two-level chain fixtures validate
the implementation; the signed fixtures were cross-checked with `openssl` raw RSA
recovery, and the footer and chain fixtures match the AOSP
`calculate_vbmeta_digest` output. Embedded-key validity is not a trust anchor:
per-location rollback handling, the lock-state-aware key check, the Pixel verifier
oracle, and real vendor hashes are pending.

### T10 - Planner v0 and dry run

**Deliverable:** vendor-order baseline, mode switches, retrofit force case,
fallback plan, plan hash, human-readable dry run.
**Accept:** golden plans for five device/package pairs; every deviation from vendor
order is annotated; brute-force equivalence on marked commutation groups.
**Depends on:** T08.
**Status:** partial (2026-11-25). Planner v0 preserves vendor order, applies wipe
filtering, annotates critical writes, computes a canonical plan hash, and emits a
stop-and-reprobe fallback. A plan is executable only when provenance is TRUE, the
package is understood, images are present, and slot/retrofit options are modeled.
Slot facts, retrofit force semantics, commutation data, and five real golden plans
are pending.

### T11 - Safety engine v0

**Deliverable:** rules SR-001, SR-002, SR-003, SR-004, SR-012, SR-013 over the
evidence graph; override policy; report header.
**Accept:** mutation tests kill every rule mutant; FALSE is never overridable;
UNKNOWN blocks unless the catalog allows it; overrides are logged with text and
provenance.
**Depends on:** T03, T09.
**Status:** partial (2026-11-25). The safety engine implements SR-001 identity,
SR-002 provenance, SR-003 AVB-chain, SR-004 rollback, SR-012 tool identity, and
SR-013 lock/key aggregation over `CheckState` inputs. FALSE is never overridable;
UNKNOWN blocks unless the rule is marked overridable; overrides record operator,
typed reason, timestamp, evidence-snapshot hash, and the exact report text, and do
not turn UNKNOWN into TRUE. Checks that claim TRUE/FALSE without evidence are
downgraded to UNKNOWN. Real AVB and rollback inputs still depend on T09/T12, CLI
wiring into `plan`/execution is pending, and mutation testing has not started.

### T12 - Rollback Oracle v0

**Deliverable:** AVB rollback indexes, catalog counters, OTA metadata hooks; result
is `TRUE`/`FALSE`/`UNKNOWN` with reasons.
**Accept:** unknown stored index plus a possibly-lowering package is a hard stop;
known-safe and definitely-lowering cases are covered; no device write is attempted
in tests.
**Depends on:** T09, T11.

### T13 - Approval binding

**Deliverable:** approval token over plan hash, snapshot hash, package hashes,
device-bound nonce, and tool versions; TOCTOU test.
**Accept:** any byte change in any bound input invalidates approval; a plan approved
for device A cannot execute on device B; test demonstrates the failure.
**Depends on:** T10, T11.

### T14 - Journal and executor happy path

**Deliverable:** write-ahead journal, idempotency classes, reconcile, crash harness
that kills at every journal point.
**Accept:** crash at every point is classified; resume reaches the same final state
in simulator; no non-idempotent op is re-run blindly.
**Depends on:** T13.

### T15 - Recovery Kit, Vault design review, M6 gate

**Deliverable:** threat model, recovery asset verification, encrypted device-bound
vault design, restore-only-same-device rule, recovery drill script.
**Accept:** external review signs off; a drill restores a backed-up partition to the
same device and refuses another device; no real write before this gate.
**Depends on:** T06, T14.

## 5. Release gates

| Gate | Milestone | Must be true |
| --- | --- | --- |
| G0 | M0 | CI green; sparse oracle in CI; simulator replays a real transcript; tool manifest and license audit exist |
| G1 | M2 | AVB/provenance matches official oracles on a real corpus; package identity is trustworthy |
| G2 | M4 | Planner, safety engine, Rollback Oracle, and approval binding pass mutation and TOCTOU tests |
| G3 | M6 | Crash harness 100%; Virtual A/B state machine simulated; Vault and recovery drill pass; external safety review |
| G4 | M7 | Three Verified devices end to end; three-shop pilot; unrecoverable-state rate measured and published |
| G5 | M10 | Samsung/EDL/MediaTek Assisted gates pass; no auth bypass; programmer/DA mismatch always vetoed |

A gate is a stop, not a suggestion. If G3 fails, no real-device writes.

- USB 2 and USB 3 ports; a known-bad cable; a powered and an unpowered hub.
- Windows 10 and 11 hosts; Ubuntu host; one WSL/VM host to test the warning.
- A bench power supply or reliable charger; battery run-down device for threshold
  tests.
- A camera/phone stand for recording device screens during first boot.

### Test matrix

Each device row records: model, region, firmware, bootloader lock state, slot count,
dynamic partition support, `max-download-size`, `max-fetch-size` presence, battery
getvars, `fastboot-info.txt` support, recovery path, and max verification level.
Rows are populated only by hardware findings.

## 7. Metrics and instrumentation

Instrument these events, opt-in and without device identifiers unless consent is
explicit:

- rule evaluated / blocked / overridden (rule ID, evidence source, duration);
- verification level per operation and per job;
- resume attempts and outcomes;
- failure classification and time to known state;
- soak throughput, error count, reconnects;
- mode switches and total job time;
- tool version and catalog version.

Dashboards per device tier. Publish the measured reliability numbers; do not publish
targets as achievements.

## 9. Decision points

- **D1 after M2:** Is package identity trustworthy enough to plan? If no, stop and
  fix provenance; do not build the planner on sand.
- **D2 after M5:** Does the crash harness pass? If no, no real-device writes.
- **D3 after M7:** Do the pilot metrics justify breadth? Reshape scope if the
  unrecoverable-state rate is above the tier ceiling.
- **D4 at M8:** Samsung go/no-go. The Maintenance Mode recovery dead-end may make
  write support a service-center product rather than a shop tool. Decide with
  hardware findings, not optimism.
- **D5 at M10:** MediaTek go/no-go. No auth bypass. If the official flow cannot
  verify or recover, stay Assisted.
- **D6 at M11:** Native USB only if measurements show the official tool is the
  bottleneck. Otherwise spend the time on reliability.

## 11. Definition of done

A task is done when:

- the behavior is implemented behind the documented interface;
- tests cover the happy path, the failure path, and the unsafe path;
- type checks, lint, and format pass;
- the safety rule or parser has a source reference or a hardware finding ID;
- the journal/report output uses verification levels correctly;
- docs (`SPEC_V2`, `SAFETY_RULES`, `DECISIONS`, `KNOWN_UNKNOWNS`) are updated;
- a real-device run, if applicable, is recorded in `HARDWARE_FINDINGS.md`;
- no non-goal was crossed.

A milestone is done when its acceptance test is reproducible by someone else from a
clean checkout.
