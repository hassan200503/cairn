# Cairn Execution Plan

**Version:** 1.0, 2026-11-24
**Companion documents:** [SPEC_V2.md](SPEC_V2.md), [ROADMAP.md](ROADMAP.md),
[SAFETY_RULES.md](SAFETY_RULES.md)

This is the build plan. It is ordered by risk retirement, not by feature appeal. The
first job is to make wrong behavior impossible to ship quietly. The second is to
prove the core on one device family. Breadth comes last.

---

## 1. Operating assumptions

- **Team:** one lead engineer (full-time) plus AI pair and part-time safety/hardware
  review. Timelines below are engineering weeks and assume this. Add 30-50% for a
  solo schedule with no hardware help.
- **Hardware:** at least two sacrificial devices per target family. Never a daily
  driver. A test device can be destroyed; the plan budgets for it.
- **Platforms:** Windows 10/11 first (repair-shop reality), Ubuntu second.
- **Release shape:** Apache-2.0 core, signed catalog as a separate commercial asset,
  opt-in telemetry.
- **No real-device writes** before the M6 gate and a documented recovery drill.
- **No auth bypass, ever.** This constrains MediaTek/Unisoc scope and is not
  negotiable.
- **One source of truth:** the spec, safety rules, decisions, unknowns, and hardware
  findings live in this repo. Chat context is not documentation.

### Cadence

- One-week thin slices; demo every Friday.
- A milestone is not done until its acceptance test runs in CI or on hardware and the
  result is recorded.
- Every safety rule change requires a mutation test and a source citation.
- Every real-device run produces a `HARDWARE_FINDINGS.md` entry and, where possible,
  a scrubbed transcript fixture.

## 2. Phase plan

| Phase | Weeks | Milestones | Exit question |
| --- | --- | --- | --- |
| P0 Foundations | 1-3 | M0 | Can we trust our parsers and simulator? |
| P1 Know before write | 4-11 | M1-M2 | Do we know what the package and host are? |
| P2 Plan and refuse | 12-19 | M3-M4 | Can we prove a plan and block unsafe jobs? |
| P3 Write safely | 20-28 | M5-M6 | Can we survive interruption and recover? |
| P4 Prove on hardware | 29-36 | M7 | Do three real devices work end to end? |
| P5 Broaden | 37-52 | M8-M10 | Can we add OTA, Samsung, and Assisted modes safely? |
| P6 Scale | 53-66 | M11-M12 | Can shops run it without an engineer? |

The critical path is **M0 -> M1 -> M2 -> M3 -> M4 -> M5 -> M6 -> M7**. Everything
else can run in parallel or slip without blocking the core.

## 4. First fifteen tasks

These are ticket-ready. Each has an acceptance test; "code exists" is not done.

### T01 - Repo and CI foundation (done)

**Deliverable:** repo, Apache-2.0 license, `pyproject.toml`, uv, ruff, mypy strict,
pytest, Hypothesis, CI on Ubuntu and Windows.
**Accept:** `uv run ruff check .`, `uv run ruff format --check .`,
`uv run mypy src`, `uv run pytest -q` all pass; CI green.
**Status:** scaffold landed in the initial commit. CI verification is part of T01's
close-out.

### T02 - Sparse oracle harness

**Deliverable:** fixtures generated by `img2simg`; round-trip and malformed-input
tests against `simg2img`; skip-with-reason only when the oracle is absent locally
(CI installs it).
**Accept:** every parser constant and header field is covered; a mutated constant
fails the suite; malformed images are rejected identically to libsparse for the
covered cases.
**Depends on:** T01.
**Status:** harness landed and green in CI (run `45500165412`): the dedicated Ubuntu
job installs `android-sdk-libsparse-utils` and the `img2simg`/`simg2img` round trip
passes. Locally the oracle skips with a reason when libsparse is absent. Malformed
cases are covered by unit tests but not yet differentially compared with libsparse.

### T03 - Evidence graph completion

**Deliverable:** evidence IDs, graph storage, freshness-at-use, post-reboot
invalidation, source strength ordering, serialization.
**Accept:** property tests for freshness and strength; a probe before reboot cannot
satisfy a post-reboot precondition; inferred evidence is never usable.
**Depends on:** T01.
**Status:** landed (2026-11-25). Evidence IDs are deterministic and verified on load;
the graph stamps facts with a boot epoch, invalidates earlier epochs on reboot, refuses
inferred and stale evidence, and survives JSON persistence. Units and source-strength
property tests are green.

### T04 - Subprocess wrapper and tool manifest

**Deliverable:** streaming subprocess runner with timeouts, cancellation, bounded
buffers, no shell, environment scrubbing; tool manifest with version, hash, minimum
version, and license.
**Accept:** simulated hang/timeout/cancel tests; a tool below minimum version is
refused; the exact version is journaled; GPL tools are only invoked as separate
processes.
**Depends on:** T01.
**Status:** runner, manifest, and tests landed (2026-11-25). Environment scrubbing,
bounded buffers, timeout, cancellation, SHA-256 and minimum-version checks are
covered. Journaling the verified version waits for the M5 journal.

### T05 - Fastboot simulator with transcripts

**Deliverable:** transcript schema, recorder/replayer, fault injection (timeout,
truncated response, `FAIL`, disconnect), `getvar all` replay.
**Accept:** simulator answers a recorded Pixel-class `getvar all`; injected faults
produce classified errors, not crashes; fixture is scrubbed.
**Depends on:** T01, T04.
**Status:** schema, recorder, replayer, faults (timeout, truncated, disconnect, fail,
garbage), and a scrubbed synthetic fixture landed (2026-11-25). Simulated evidence is
forced to `INFERRED` so it can never satisfy a safety rule.

### T06 - Fastboot adapter, read-only

**Deliverable:** detect, `getvar`, slot/capability/battery probes, lock state, device
identity. No write path yet.
**Accept:** adapter passes against simulator and one real device; every fact carries
provenance and freshness; unknown values stay `UNKNOWN`.
**Depends on:** T05.
**Status:** partial (2026-11-25). Read-only `getvar all`/`getvar`, provenance,
freshness, and fail-closed classification pass against the simulator; one real-device
run is still required. Slot signals are recorded as `UNKNOWN` values until a hardware
finding confirms their semantics.

### T07 - Host Doctor MVP and link soak

**Deliverable:** Windows driver presence checks, USB topology, power/sleep checks,
WSL/VM warning, antivirus heuristic, soak test using `getvar` and staged `download`.
**Accept:** a bad cable/port/hub scenario is detected and blocks; a healthy setup
passes; results are recorded with thresholds and tool versions.
**Depends on:** T04, T06.
**Status:** MVP landed (2026-11-25). Read-only checks cover WSL/VM, USB controllers,
a Windows driver-package heuristic, USB selective suspend, antivirus heuristics,
tool versions, and a bounded `getvar` soak with explicit failure/latency thresholds.
A failed soak is FALSE and blocks. Staged-download soak and USB topology depth remain
pending.

### T08 - Package parsers and unified manifest

**Deliverable:** factory zip, `fastboot-info.txt`, sparse images, OTA metadata
read-only, unified `PackageManifest`.
**Accept:** golden fixtures for at least three vendor packages; unknown files are
reported, not ignored; malformed archives fail closed.
**Depends on:** T02, T04.
**Status:** partial (2026-11-25). The AOSP v1 `fastboot-info.txt` grammar, full
sparse-image validation, factory/OTA zip inspection, OTA metadata, and the unified
`PackageManifest` are implemented, with a read-only `cairn inspect`. Synthetic
fixtures cover the parsers; golden fixtures for three real vendor packages are still
required, and nested factory image zips are reported but not opened.

### T09 - Provenance and AVB chain verification

**Deliverable:** vendor hash index, `avbtool` chain-following verification, VBMeta
digest, lock-state-aware key check, `pixel_factory_image_verify.py` oracle.
**Accept:** matches `avbtool` and the Pixel verifier on a corpus; chained VBMeta and
per-location rollback indexes are handled; unknown package is Assisted, not Verified.
**Depends on:** T08.
**Status:** partial (2026-11-25). The offline vendor hash index and `cairn provenance`
are implemented with strict schema validation, archive/entry hash comparison, and
tri-state results; a local index match is explicitly not a signature check. A strict
read-only VBMeta parser (`provenance/avb.py`) and `cairn avb info|digest|verify`
now parse standalone, padded, and footer-embedded VBMeta headers and hash,
hashtree, chain, property, and kernel cmdline descriptors, compute the AOSP digest
from supplied chained images, and verify the VBMeta RSA signature against the
embedded key with an optional expected raw AVB public key. Chain-of-trust
verification (`verify_vbmeta_chain`, `cairn avb verify --chain NAME=PATH`) checks
that each chain descriptor's key equals the chained image's embedded key, that the
chained signature validates, that the descriptor rollback location is non-zero
while the chained header location is zero, and that nested chains hold, with
tri-state fail-closed results where FALSE outranks UNKNOWN outranks TRUE. AOSP
avbtool-generated unsigned, signed, footer, and two-level chain fixtures validate
the implementation; the signed fixtures were cross-checked with `openssl` raw RSA
recovery, and the footer and chain fixtures match the AOSP
`calculate_vbmeta_digest` output. Embedded-key validity is not a trust anchor.
Per-location rollback handling and an offline lock-state-contextual expected-key
check (`cairn avb key-check`) are implemented. The key check handles invalid
signatures, locked mismatches, unlocked mismatches, and unknown inputs fail-closed,
but its lock state and key are caller-supplied and cannot satisfy SR-013 by itself.
The Pixel verifier oracle, device lock/key binding, and real vendor hashes are
pending.

### T10 - Planner v0 and dry run

**Deliverable:** vendor-order baseline, mode switches, retrofit force case,
fallback plan, plan hash, human-readable dry run.
**Accept:** golden plans for five device/package pairs; every deviation from vendor
order is annotated; brute-force equivalence on marked commutation groups.
**Depends on:** T08.
**Status:** partial (2026-11-25). Planner v0 preserves vendor order, applies wipe
filtering, annotates critical writes, computes a canonical plan hash, and emits a
stop-and-reprobe fallback. A plan is executable only when provenance is TRUE, the
package is understood, images are present, and slot/retrofit options are modeled.
Slot facts, retrofit force semantics, commutation data, and five real golden plans
are pending.

### T11 - Safety engine v0

**Deliverable:** rules SR-001, SR-002, SR-003, SR-004, SR-012, SR-013 over the
evidence graph; override policy; report header.
**Accept:** mutation tests kill every rule mutant; FALSE is never overridable;
UNKNOWN blocks unless the catalog allows it; overrides are logged with text and
provenance.
**Depends on:** T03, T09.
**Status:** partial (2026-11-26). The safety engine implements SR-001 identity,
SR-002 provenance, SR-003 AVB-chain, SR-004 rollback, SR-012 tool identity, and
SR-013 lock/key aggregation over `CheckState` inputs. FALSE is never overridable;
UNKNOWN blocks unless the rule is marked overridable; overrides record operator,
typed reason, timestamp, evidence-snapshot hash, and the exact report text, and do
not turn UNKNOWN into TRUE. Checks that claim TRUE/FALSE without evidence are
downgraded to UNKNOWN. `cairn plan` now binds its structural candidate to a
SafetyReport and returns executable only if both gates pass; its JSON separates
`structurally_executable` from `executable` and includes the evidence snapshot.
It feeds only the provenance evidence it actually has, so SR-001/003/004/012/013
remain UNKNOWN and block until a catalog-bound preflight collects those inputs.
Mutation testing of the safety rules landed with T19 (`tools/mutation_check.py`):
33/33 mutants killed across all 11 registered rules.

### T12 - Rollback Oracle v0

**Deliverable:** AVB rollback indexes, catalog counters, OTA metadata hooks; result
is `TRUE`/`FALSE`/`UNKNOWN` with reasons.
**Accept:** unknown stored index plus a possibly-lowering package is a hard stop;
known-safe and definitely-lowering cases are covered; no device write is attempted
in tests.
**Depends on:** T09, T11.
**Status:** partial (2026-11-26). The Rollback Oracle v0 (`rollback/oracle.py`) applies
the AOSP rollback inequality — the device rejects an image unless
`rollback_index[n]` >= `stored_rollback_index[n]` for every location `n` — to the
counters a VBMeta package declares, including chained partitions at the location
named by the chain descriptor; nested chain descriptors are followed with a depth
limit, and missing or malformed chained counters are unresolved. It returns a
tri-state verdict with per-counter reasons. The device's stored value is
authoritative when it can be read; otherwise a catalog bound can prove safety
(upper bound) or prove a downgrade (lower bound); an unknown stored value is
UNKNOWN, a hard stop, and never overridable. `cairn rollback check` exposes the
check with `--chain` and `--stored LOCATION=VALUE`; it parses chain images but
does not verify their signatures. `cairn rollback read` and
`rollback check --device` add a vendor-specific stored-index reader for the
observed `stored_rollback_index` and `avb_stored_rollback_indexes` getvar forms;
absence, conflicts, malformed values, truncation, or a failed command are
UNKNOWN, and OEM signals such as `ap-ar-s` are warnings rather than AVB indexes.
Pending: a generic AOSP path, an EDL fallback, real scrubbed transcripts, OEM
counter policy, OTA downgrade metadata evaluation, and wiring the oracle result
into SR-004 and the plan path.

### T13 - Approval binding

**Deliverable:** approval token over plan hash, snapshot hash, package hashes,
device-bound nonce, and tool versions; TOCTOU test.
**Accept:** any byte change in any bound input invalidates approval; a plan approved
for device A cannot execute on device B; test demonstrates the failure.
**Depends on:** T10, T11.

### T14 - Journal and executor happy path

**Deliverable:** write-ahead journal, idempotency classes, reconcile, crash harness
that kills at every journal point.
**Accept:** crash at every point is classified; resume reaches the same final state
in simulator; no non-idempotent op is re-run blindly.
**Depends on:** T13.
**Status:** partial (2026-11-27). `cairn.executor` lands the append-only,
hash-chained, fsync-per-record JSONL write-ahead journal (torn tails are detected
and truncated on resume; mid-chain corruption refuses the journal) and the
simulator-gated plan executor behind three fail-closed gates: plan hash plus
executability, the pre-approval safety verdict (FALSE refuses always; UNKNOWN is
executable only in the simulator and the run stays labelled `SIMULATED`), and a
verified approval token over plan, package, entry hashes, and device binding
(SR-018). Every flashed image is re-extracted and re-hashed against the approval
bundle before staging. Idempotency classes: flash/erase/update-super may re-run on
resume; an interrupted reboot aborts with stop-and-reprobe and demands a fresh
preflight; a previously failed step is never retried. The crash harness kills
execution after every journal record and proves each resume reaches the exact
uninterrupted final state (`tests/test_executor.py`); `cairn execute` wires this to
the CLI and refuses real fastboot binaries (`ADR-027`). The T26 slice added the
journal growth/rotation policy (a journal nearing its 32 MiB limit is rotated at
resume time into a verified continuation chain; predecessors stay on disk as
evidence) and pre-write slot/VAB reconciliation: the executor reads
`snapshot-update-status` and `current-slot` through the transport's read-only
seam, journals a `reconciled` record, and aborts on a mid-merge state (SR-010
FALSE; UNKNOWN is journaled as a warning in the simulator-only executor).
Pending: the real-device transport behind T15 and the M6 gate.

### T15 - Recovery Kit, Vault design review, M6 gate

**Deliverable:** threat model, recovery asset verification, encrypted device-bound
vault design, restore-only-same-device rule, recovery drill script.
**Accept:** external review signs off; a drill restores a backed-up partition to the
same device and refuses another device; no real write before this gate.
**Depends on:** T06, T14.
**Status:** partial (2026-11-27). The threat model
(`docs/RECOVERY_THREAT_MODEL.md`), the SR-008 asset verification and readiness
check, the encrypted device-bound vault (HMAC-SHA256-CTR encryption,
encrypt-then-MAC over the canonical document, plaintext sha256 re-verification
on decrypt, unsafe partition names refused), the restore-only-same-device rule
(`VaultDeviceMismatch`, never overridable), and the `cairn recovery
backup|verify|restore|drill` CLI landed (ADR-028). The T25 slice moved the
vault to format v2 (ADR-029): PBKDF2-HMAC-SHA256 at 600,000 iterations, the
KDF block pinned inside the MACed document, v1 files refused with a pointer to
the ADR; `docs/REVIEW_BUNDLE.md` now packages the scope, reproduction steps,
and required sign-off contents for the KU-032 reviewers. The drill proves the
same-device round trip and the cross-device refusal through the journaled
transcript simulator only (`tests/test_recovery.py`,
`tests/test_cli_recovery.py`); real fastboot is refused per ADR-027. Pending:
the external crypto review of the vault and external safety review of the
drill (KU-032) — the drill passing is necessary, not sufficient, for the M6
gate — plus real scrubbed transcripts, hardware findings, and the Virtual A/B
/ dynamic partition state machines.

### T16 - Virtual A/B merge-state gate

**Deliverable:** read `snapshot-update-status`, classify it tri-state, enforce
SR-010 in the safety engine, expose a read-only status command.
**Accept:** every reported state (none, snapshotted, merging, unrecognized, FAIL,
absent) maps to the SAFETY_RULES SR-010 verdicts; an unrecognized value or a FAIL
blocks; no override; the read is read-only on a real device and replayable from a
transcript.
**Depends on:** T06, T11.
**Status:** landed (2026-11-27). `cairn.vab` reads `snapshot-update-status` with
one read-only `getvar` and classifies it: `none` is TRUE;
`snapshotted`/`merging`/`merge_pending` are a never-overridable FALSE (a flash
during an unfinished merge can leave the device unbootable); an unrecognized
vendor value or a failed read is UNKNOWN and blocks (KU-004 stays open for
vendor-specific states). The gate is safety-engine rule SR-010 (blocking, not
overridable) and the CLI command `cairn vab status`. Remaining work: the
super/dynamic-partition metadata state machine (SR-011) and explicit
operator-approved merge/cancel flows modeled as plans; cairn never auto-cancels.

### T17 - Dynamic-partition mode gate

**Deliverable:** read the dynamic-partition facts, evaluate the flash mode
against the job's requirement, enforce SR-011 in the safety engine, expose a
read-only mode check.
**Accept:** a fastbootd job from the bootloader is FALSE and never overridable;
unreadable facts are UNKNOWN and block; a bootloader job on a dynamic device is
not a silent pass; the read is read-only and transcript-replayable.
**Depends on:** T06, T11, T16.
**Status:** landed (2026-11-27). `cairn.vab.dynpart` reads `is-userspace`,
`dynamic-partition`, and `super-partition-name` with three read-only getvars and
evaluates the job's required mode. The gate is safety-engine rule SR-011
(blocking; UNKNOWN is typed-overridable per SAFETY_RULES, FALSE is never
overridable) and the CLI command `cairn vab dynpart --mode fastbootd|bootloader`.
Remaining work: real super metadata parsing behind lpunpack/lpmake oracles and
modeled operator-approved merge/cancel flows.

### T18 - Modeled snapshot cancel and merge flows

**Deliverable:** explicit operator-approved cancel and merge flows with typed
acknowledgment, recovery readiness, and a matching merge-state precondition,
runnable only against the transcript simulator.
**Accept:** cancel refuses a `none` device; merge refuses a merely `snapshotted`
device; a mismatched or paraphrased acknowledgment is refused; unverified
recovery assets are refused; every write reaches the transcript replay only.
**Depends on:** T14, T15, T16.
**Status:** landed (2026-11-27). `cairn.vab.flows` gates `cairn vab cancel|merge`
behind the merge-state precondition, an exact typed acknowledgment sentence,
`verify_assets` recovery readiness plus a stated last-resort path (SR-008), and a
`SimulatedFastbootTransport` (ADR-027). The executor gained the
`snapshot-update` PlanAction with a `cancel`/`merge` target check. Cairn never
auto-cancels. Remaining work: super metadata parsing oracles and the external
reviews (KU-032).

### T19 - Safety-rule mutation harness

**Deliverable:** an on-demand mutation runner that mutates each registered
safety-rule evaluator and proves the suite kills it.
**Accept:** every rule in `DEFAULT_RULES` has at least three suite-killed
mutants; the harness leaves the engine source byte-identical after a run.
**Depends on:** T11.
**Status:** landed (2026-11-27). `tools/mutation_check.py` (stdlib only) wraps
each rule's registration in `DEFAULT_RULES` with three mutants — `always-true`,
`unknown-true` (the silent-pass mutant), and `false-true` (the unsafe-pass
mutant) — and runs the safety-relevant test files in a subprocess per mutant.
Recorded run: **33/33 mutants killed** across SR-001, 002, 003, 004, 008, 009,
010, 011, 012, 013, and 018. The harness fails loudly if a refactor changes a
registration site, and restores the engine byte-exactly in all paths. Run it
after any change to rule logic; it is not in the default CI loop (roughly three
minutes). Approval-binding mutation tests remain separate future work.

### T20 - Approval-binding mutation tests

**Deliverable:** mutation tests over the approval token, binding, and device
fingerprint code, run by the same harness.
**Accept:** skipping any bound-field comparison, the MAC, the binding-hash or
key-id check, or dropping a fingerprint fact is killed by the suite; the harness

**Depends on:** T13, T19.
**Status:** landed (2026-11-27). The harness gained an `approval` mutant family:
field-comparison removals (plan, evidence snapshot, archive, device, package

### T21 - Super metadata parser (SR-011 metadata half)

**Deliverable:** parse `super.img`/dynamic-partition metadata (geometry and LP
metadata) so the planner can confirm the on-device partition layout before a
write.
**Accept:** parser output is differentially tested against an official oracle
(`lpunpack`/`lpdump`/`lpmake`), per AGENTS.md rule 9; golden fixtures carry the
generating command and SHA-256.
**Depends on:** T17.
**Status:** landed (2026-11-27), together with the T24 oracle. The official
AOSP `lpmake` host tool is built from pinned source in a dedicated CI job
(`tools/oracle/build_lpmake.sh`; pins in `tools/oracle/PINNED.md`; SHA-256
shim and host liblog stub documented there — libcrypto's only use in liblp is
SHA-256, and the Python parser independently recomputes every checksum with
`hashlib`, so the differential tests police the shim). `cairn.vab.super_meta`
parses both on-disk layouts (full super; empty super from
`--device-size auto`), validates geometry/header/table checksums, versions,
table bounds and entry sizes, partition-name charset and uniqueness, the
attribute mask, and extent targets, and raises `SuperMetadataError` on any
anomaly (callers must treat that as UNKNOWN). Tests: golden fixture with a
pinned SHA-256 generated by the oracle, differential tests against fresh
oracle output (full, super-empty, slot-suffixing; CI-enforced), negative
checksum/truncation tests. Remaining work: wire the parsed layout into a
rule or the planner; real-device `super.img` fixtures (KU-016, KU-033's
remaining hardware half).

### T23 - Read-only probe capture (hardware-finding factory)

**Deliverable:** a one-command capture that runs the `getvar all` plus
checklist probes of `HARDWARE_FINDINGS.md` §5 against a real device, journals
every invocation in a transcript, scrubs serials, and emits a finding-template
draft.
**Accept:** no write verb is ever recorded; a raw serial cannot survive
scrubbing (scrub raises instead of passing one through); the finding draft
follows the §2 template; tests cover happy, refusal (`--simulate` conflict),
and scrub-everywhere paths.
**Depends on:** T06, T14 (transcript schema).
**Status:** landed (2026-11-27). `cairn.adapters.capture` (`run_capture`,
`scrub_transcript`, `write_capture`) and `cairn probe --capture DIR` write
`transcript.json` + `finding.yaml` into a caller-provided directory and print
the transcript SHA-256. Captures are labelled as single observations; a
finding is promoted only after reproduction (§3 of `HARDWARE_FINDINGS.md`).
The Windows `.cmd` batch test double must avoid parentheses inside `if (...)`
blocks — `cmd` mis-parses `echo (bootloader) ...` there.

### T29/T30 - Device catalog and lock/key anchoring (KU-031 schema half)

**Accept:** every entry cites a source (uncited entries are refused, per rule 2);

**Depends on:** T09.
**Status:** landed (2026-11-27). `cairn.catalog` (`DeviceCatalog`,

key-check --catalog …` with `--device-fingerprint`/`--product` selection.
`cairn wizard --catalog` anchors the AVB stage the same way: the entry is
selected by the caller fingerprint or the probed device record, and the

## 9. Decision points

- **D1 after M2:** Is package identity trustworthy enough to plan? If no, stop and
  fix provenance; do not build the planner on sand.
- **D2 after M5:** Does the crash harness pass? If no, no real-device writes.
- **D3 after M7:** Do the pilot metrics justify breadth? Reshape scope if the
  unrecoverable-state rate is above the tier ceiling.
- **D4 at M8:** Samsung go/no-go. The Maintenance Mode recovery dead-end may make
  write support a service-center product rather than a shop tool. Decide with
  hardware findings, not optimism.
- **D5 at M10:** MediaTek go/no-go. No auth bypass. If the official flow cannot
  verify or recover, stay Assisted.
- **D6 at M11:** Native USB only if measurements show the official tool is the
  bottleneck. Otherwise spend the time on reliability.

## 11. Definition of done

A task is done when:

- the behavior is implemented behind the documented interface;
- tests cover the happy path, the failure path, and the unsafe path;
- type checks, lint, and format pass;
- the safety rule or parser has a source reference or a hardware finding ID;
- the journal/report output uses verification levels correctly;
- docs (`SPEC_V2`, `SAFETY_RULES`, `DECISIONS`, `KNOWN_UNKNOWNS`) are updated;
- a real-device run, if applicable, is recorded in `HARDWARE_FINDINGS.md`;
- no non-goal was crossed.

A milestone is done when its acceptance test is reproducible by someone else from a
clean checkout.
